# 디자인과 아트 규칙

이 문서는 에이전트가 내용을 바꾸면서 시각적 일관성을 유지하기 위한 기준이다. 특정 개인의 프로젝트 구조나 수치를 전제로 하지 않는다.

## 화면 구성

- 넓은 화면은 `250px / 나머지`의 두 열이다. 왼쪽은 이름·관심 분야·프로젝트 선택·소개와 기록·공개 링크다. 오른쪽은 선택한 프로젝트의 화면이다.
- 오른쪽의 읽는 순서: 프로젝트 이름·기간 → 핵심 제목 → 소개·역할 → 큰 그림 → 사용 기술과 공개 링크.
- "만든 과정 보기"를 누르면 같은 영역에서 글을 읽는다. `/projects/<id>/` 상세 주소는 직접 열거나 공유할 수 있다.
- 모바일은 소개와 프로젝트 목록이 위에 온다. 프로젝트 선택은 가로로 넘긴다. 본문은 독립적으로 스크롤된다. 세로 공간이 작은 화면에서 제목이나 조작 버튼을 잘라 먹지 않는다.
- 프로젝트가 늘어나도 왼쪽 목록과 본문 스크롤을 유지한다. 빈 프로젝트 목록은 소개 화면으로 시작한다. 없는 경력·기술·글을 가짜로 채워 레이아웃을 맞추지 않는다.

## 색과 표면

| 역할 | 밝은 화면 | 어두운 화면 |
|---|---|---|
| 종이 `--paper` | `#ffffff` | `#151319` |
| 주 글자 `--ink` | `#171717` | `#e7e5eb` |
| 보조 글자 `--ink-2` | `#626262` | `#b7b3bb` |
| 선 `--line` | `#e3e3e3` | `#2c2830` |
| 그림 바탕 `--stage` | `#fafafa` | `#110f15` |
| 제목 강조 `--signal` | `#c04466` | `#e36986` |

- 어두운 회색은 약한 보랏빛을 띤다. 순수 검정으로 일괄 치환하지 않는다.
- 그림 바탕은 종이보다 한 톤 어둡게 둔다. 글과 도식이 같은 표면에서 읽혀야 한다.
- 큰 색 면, 무지개 기술 배지, 카드마다 다른 그라디언트, 장식용 유리 패널을 추가하지 않는다.
- 기본 구분선은 1px, 큰 시작점은 2px이다. 모서리를 둥글게 만드는 것으로 계층을 대신하지 않는다.
- 선택한 프로젝트는 바탕과 글자색을 뒤집어 표시한다. 색만으로 선택 상태를 전달하지 않고 `aria-current`도 유지한다.

## 글자와 간격

- 본문: 로컬 Pretendard Variable. 숫자와 짧은 영문 라벨: 로컬 Geist Mono. 외부 글꼴 요청을 추가하지 않는다.
- 크기 계층은 제목, 본문, 보조 라벨로 제한한다. 제목이 시선을 먼저 끌고, 본문이 편하게 읽혀야 한다.
- 큰 제목은 대략 30~60px, 본문은 14~17px, 보조 라벨은 10~13px 범위다. 모바일 핵심 제목은 28~42px다. 길어진 문장을 억지로 작게 줄이지 말고 문장을 먼저 다듬는다.
- 제목은 약한 음수 자간과 1.16 전후의 줄높이, 본문은 1.7~1.9의 줄높이를 쓴다. 한국어 단어를 무리하게 쪼개지 않는다.
- 한 제목의 강조는 실제 핵심 단어 한 덩어리로 제한한다. `accent`가 `title`에 존재해야 한다.
- 긴 글은 최대 약 960px의 읽기 폭을 둔다. 섹션 제목과 본문을 분리하고, 문단 사이에 충분한 여백을 둔다.

## 빛으로 그리는 그림

`light-field.tsx`는 프로젝트 데이터와 분리된 범용 점광원 렌더러다. `project-art.tsx`가 좌표·크기·밝기를 제공한다.

1. **투명한 바탕:** 점이 없는 곳은 화면의 바탕이 그대로 보인다. 검정 사각형이나 흰 이미지 배경을 덧씌우지 않는다.
2. **하나의 밝기 체계:** 점을 더하고, 약한 번짐을 더한 뒤, 합산 밝기에 따라 색을 정한다. 객체마다 임의의 무지개색을 지정하지 않는다.
3. **밝은 화면 팔레트:** 살구 → 산호 → 장미 → 자주 → 짙은 보라. 셰이더의 `flare()`가 기준이다.
4. **어두운 화면 팔레트:** 인디고 → 마젠타 → 오렌지 → 앰버. 셰이더의 `ramp()`가 기준이다.
5. **깊이:** 원근, 겹침, 점의 밝기와 크기로 형태가 읽히게 한다. 라벨은 읽을 수 있는 평면 글자로 남긴다.
6. **움직임:** 느린 회전과 작은 포인터 반응만 사용한다. 과한 확대·빠른 카메라·자동 화면 전환·소리는 기본으로 추가하지 않는다.
7. **접근성:** `prefers-reduced-motion: reduce`에서는 정지된 시간의 그림을 보인다. WebGL을 사용할 수 없으면 CSS 윤곽으로 대체한다. 장식이 없어도 내용을 이해할 수 있어야 한다.
8. **성능:** 하나의 선택된 장면만 렌더링한다. 화면을 벗어나거나 컴포넌트가 해제되면 관련 프레임·버퍼·관찰자를 정리한다. 디바이스 픽셀 비율은 최대 2로 제한한다.

### 기본 그림 선택

| 값 | 형태 | 성격 |
|---|---|---|
| `orbit` | 빛의 고리와 중심 | 추상 장식 |
| `layers` | 겹친 점의 평면 | 추상 장식 |
| `flow` | 나란히 흐르는 점의 물결 | 추상 장식 |
| `none` | 절제된 글자 면 | 장식 없이 소개 |

세 기본 그림은 실제 시스템의 구성이나 측정 결과를 뜻하지 않는다. `artLabels`도 데이터의 증거가 아니다. 장식용 그림이라는 표시를 유지하고, 측정 결과처럼 오해하게 만드는 숫자나 축을 넣지 않는다.

### 실제 프로젝트 도식을 요청받았을 때

- 먼저 프로젝트의 실제 입력·처리·출력, 사용자 흐름, 본인 구현 범위를 인터뷰한다.
- 단계를 도식화할 때는 실제 단계만 그린다. 화살표는 입력·호출·데이터 이동 중 무엇을 뜻하는지 설명할 수 있어야 한다.
- 한 그림은 하나의 질문에 답한다. 구성 전체, 특정 문제의 원인, 해결 전후를 한꺼번에 넣지 않는다.
- 2~4개의 핵심 덩어리로 시작하고, 세부는 다음 그림이나 본문으로 옮긴다. 라벨은 짧고 선과 겹치지 않게 한다.
- 성능 그래프는 실제 측정치·단위·조건·출처가 있을 때만 만든다. 보기 좋은 곡선을 먼저 그리고 수치를 붙이지 않는다.
- 사진·화면 캡처는 원본 비율을 유지한다. `imageAlt`에 읽는 데 필요한 정보를 적는다. 사용자·팀원·고객 정보가 노출됐는지 확인한다.
- 새 그림도 위의 동일한 팔레트·바탕·명암·깊이 규칙을 따른다. 내용 교체 요청을 전체 디자인 변경으로 확대하지 않는다.

## 완료 전 화면 확인

- 1440×900: 왼쪽 레일과 제목·그림·버튼이 읽기 순서대로 보이는가?
- 960×1080: 상단 레일로 접혔을 때 프로젝트 목록과 본문이 겹치지 않는가?
- 390×844: 제목, 가로 메뉴, 본문이 잘리지 않고 스크롤되는가?
- 밝은/어두운 테마에서 본문·선·강조·그림이 충분히 구분되는가?
- 키보드로 메뉴와 버튼을 조작할 수 있고, 초점이 보이는가?
- 움직임 줄이기와 WebGL 미지원에서도 글을 읽고 이동할 수 있는가?
- 프로젝트명과 문단이 길어져도 가로 스크롤이나 겹침이 생기지 않는가?
