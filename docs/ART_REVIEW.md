# 아트 제작·검수·응답 규격

## 1. 먼저 알아낼 것 — 미감을 사용자에게 떠넘기지 않기

`AGENTS.md`의 경험 인터뷰를 유지한다. 구체적인 내용이 부족하면 묻되, 이미 정해진 아트 스타일을 다시 고르게 하지 않는다.

사용자에게 물어야 할 것: 이 장면이 보여 줄 결정, 실제 입력·출력, 무엇이 실패했고 무엇이 바뀌었는지, 본인 기여, 실제 자료와 공개 범위, 강조해야 할 의미. 이미 자료에 있으면 읽고 확인한다.

에이전트가 책임질 것: 실루엣·배치·밀도·색·빛·시차·라벨·선·카메라·반응형·오류 수정. "어느 부분이 구린가요?", "어떤 미감이 좋으세요?", "참고 사이트를 골라 주세요"를 기본 대응으로 쓰지 않는다. 사용자가 미감을 말로 설명하지 못해도 제작은 가능해야 한다.

"어떻게 하면 좋을까?"처럼 제안을 요청하면 짧게 제안부터 한다. "고쳐", "만들어", "해봐"라고 요청했으면 승인받기 위해 다시 멈추지 않고 실제 비교 가능한 장면을 만든다. 질문과 실행 요청을 구분한다.

## 2. 제작 전 12개 항목

에이전트가 아래를 비공개 제작 메모에 적는다. 사용자에게 빈 양식을 전부 채우라고 보내지 않는다. 실제 사실을 모르는 항목만 2~5개씩 묻는다.

1. 이 장면을 10초 보고 이해할 주장 한 문장은 무엇인가?
2. 그 주장이 작성자의 어떤 행동·판단을 보여 주는가?
3. 주인공 물체와 보조 문맥은 무엇인가?
4. 보일 사건은 전후·실패/성공·포함·흐름 중 무엇인가?
5. 입력·출력·분기·시간·축에서 바꾸면 안 되는 사실은 무엇인가?
6. 이해를 위해 압축·대표화·평활할 것은 무엇인가?
7. 기존에 재사용할 심볼과 반드시 같은 원본을 쓸 대상은 무엇인가?
8. 빛 / 잉크와 원본 색 / 종이 중 어떤 문법이 내용에 맞는가?
9. 밝은 테마에서도 남는 핵심 실루엣은 무엇인가?
10. 연결선·라벨·값은 각각 무엇을 가리키는가?
11. 움직임 없이도 읽히는 대표 상태와, 움직임이 추가할 정보는 무엇인가?
12. 첫 진입·재방문·루프·작은 창에서 무엇을 확인해야 하는가?

## 3. 제작 순서

1. `ART_STYLE.md`와 관련 실패 기록을 읽고 장면의 주장을 정한다.
2. 기본 형태와 배치를 정지 상태에서 완성한다. 작은 입력·처리기·출력을 빈 공간에 흩어 놓은 상태에서 이펙트 작업으로 넘어가지 않는다.
3. 심볼 원본과 라벨 기준을 통일하고 전후·변경점이 읽히게 만든다.
4. 표면·명암·팔레트를 두 테마에서 다듬는다. 전체 밝기 증가가 해법이라고 가정하지 않는다.
5. 사건·시차·카메라·전환을 추가한다. 불필요한 과장과 의미 없는 움직임을 걷는다.
6. 낮은 노트북 창·절반 창·휴대폰에 맞춘다. 좋아한 넓은 화면 구도를 무너뜨리지 않는다.
7. 아래 의미 검사와 동작 검사를 수행하고 결함을 고친다.
8. 새 빌드로 실제 미리보기를 열고 결과를 보고한다. 오래된 `out/`을 새 구현이라고 보여 주지 않는다.

독립된 큰 변경은 비교 가능하게 만든다. 바뀌는 축은 한 번에 식별 가능해야 한다. 한 시안에서 모양·색·서사·순서를 동시에 바꾸고 무엇이 나아졌는지 알 수 없게 만들지 않는다.

## 4. 의미 검사

긴 설명 문단을 보지 않고 그림과 최소 이름표만으로 다음을 답해 본다. 가능한 도구가 있으면 기대 정답을 모르는 독립 검토자나 새 문맥의 에이전트에게도 같은 질문을 한다. 자료를 다른 외부 서비스에 무단 업로드하지 않는다.

- 무엇이 들어와 무엇이 나오는가?
- 어떤 대상·상태·사건을 비교하는가?
- 무엇이 바뀌었고, 무엇은 그대로인가?
- 이 그림에서 작성자의 선택과 그 이유는 무엇인가?
- 원인·결과·학습·실행의 경계가 뒤집혀 보이지 않는가?

검토자에게는 최소 분야 배경과 실제 그림을 주되 정답을 담은 캡션·원본 제작 메모·구현 코드·의도 설명을 먼저 주지 않는다. 원래 대화를 모두 아는 에이전트의 재진술은 독립적인 읽기 검사가 아니다.

"입력 → 모델 → 결과" 같은 일반론만 나오면 그 장면의 고유 주장은 전달되지 않은 것이다. 짧은 이름표는 허용한다. 오히려 모든 라벨을 지워 알아맞히기 게임으로 만들지 않는다.

의미 검사가 실패하면 라벨을 늘리기 전에 주인공·비교·배치·사건을 고친다. 검사를 못 했으면 미실시로 적는다. 통과했다고 사용자 미감 수락으로 바꾸지 않는다.

## 5. 미감 검사 — 반드시 물을 것

- 주요 형태가 하나의 덩어리로 읽히는가, 작은 점과 선의 군집처럼 흩어져 있는가?
- 주인공이 충분히 크고, 입력·처리·출력의 비율이 완성되어 있는가?
- 실루엣·윤곽·내부 밀도·활성 부분의 대비가 구별되는가?
- 받침대·격자·축·가이드가 데이터를 덮고 있지 않은가?
- 긴 빈 연결 구간과 의미 없는 장식이 있는가?
- 밝은 화면에서 핵심이 흐린 점으로 사라지지 않는가?
- 어두운 화면에서 블룸이 탁하거나 모든 선이 같은 색으로 포화되지 않는가?
- 같은 대상은 같은 심볼이며, 작은 크기에서도 알아볼 수 있는가?
- 선의 각도·꺾임·라벨 착지·값의 정렬이 통일되어 있는가?
- 특정 장면만 다른 그림 세트에서 가져온 것처럼 보이지 않는가?
- 제목이 크기만으로 과장되어 그림 자리를 줄이거나 본문과 경쟁하지 않는가?
- 출처·실제 데이터가 맞다는 설명을 빼도 그림 자체가 매력적인가?

## 6. 창·테마·동작 검사 기록

| 항목 | 결과에 반드시 남길 것 |
|---|---|
| 1440×668 | 주인공 크기·낮은 높이·버튼·라벨 겹침 |
| 1440×900 또는 1920×1080 | 전체 구도·레일·과한 빈 공간 |
| 960×1080 또는 1110×908 | 위로 접힌 레일·절반 창·내용 폭 |
| 390×844 | 조작·긴 제목·스크롤·그림 가독성 |
| 밝음 / 어두움 | 잉크·신호·원본색·번짐·캔버스 경계 |
| 움직임 줄이기 | 정보가 남은 대표 정지 상태·포인터 반응 제한 |
| WebGL 없음 또는 실패 | 뜻을 남긴 대체 그림·조작·링크 |
| 처음·재방문·뒤로 가기 | 초기화 정책·현재 장면·자원 중복 |
| 전환 중간·종료 | 접점·카메라 착지·UI 위치·이벤트 완료 |
| 두 레일의 네 조합 | 옆/옆·위/옆·옆/위·위/위에서 이름·현재 위치·돌아가기와 읽기 공간. [DETAIL_UX.md](DETAIL_UX.md) 기준 |
| 루프 경계 | 시간 창·입자·핀·상태·소리의 새 시작 |

각 결과는 `통과 / 결함 수정 후 통과 / 미확인 / 해당 없음` 중 하나와 관찰 근거를 적는다. 추측으로 통과 처리하지 않는다. 자동 캡처와 실제 GPU·실기기에서 확인한 범위를 구분한다.

캡처는 정렬·겹침·정지 실루엣 검사에 쓴다. 실제 움직이는 미리보기에서 지터·속도·반응·이음새도 확인한다. 사용자가 눈으로 볼 결과에는 로컬 또는 배포 주소와 정확한 화면 위치를 제공한다. JSON·코드 파일 링크만으로 아트를 보고했다고 하지 않는다.

## 7. 사용자에게 아트 작업을 보고하는 규격

전체 대화 형식은 `AGENTS.md`를 따른다. 구현 보고의 세 항목 안에 아래 내용을 포함한다.

**반영한 내용**
- 지금 → 바꾼 것 → 그림에서 달라 보이는 의미, 순서로 짝지어 적는다.
- 보존한 구도·심볼·사실과 바꾼 축을 명시한다. "더 미려하게"라는 평가만 쓰지 않는다.

**확인 중인 점**
- 살아 있는 미리보기 주소·장면 위치·보기 방법을 준다.
- 의미·미감·창 크기·테마·전환 검사를 구별하고 미확인 항목을 숨기지 않는다.
- 자기 평가나 독립 검사 통과를 사용자의 수락으로 쓰지 않는다.

**다음 작업**
- 실제 결함과 남은 확인을 구체적으로 적는다. 이미 요청받은 수정은 스스로 이어서 처리한다.
- 막연히 "어디가 별로인가요?"라고 하지 않는다. 사실·의미가 불명확한 부분만 구체적으로 묻는다.

## 8. 회귀 검사와 커밋

`npm run check-art`는 자유 색 토큰의 형식·CSS/셰이더 연결, 폰트 범위, 필수 문서와 로컬 문서 링크를 검사한다. 특정 색을 강제하지 않는다. 테스트·빌드는 다음을 포함한다.

```sh
npm run check-art
npm test
npm run build
npm run check-types
```

사용자가 원하는 색은 `content/theme.json`에서 자유롭게 바꾸고 정상 통과해야 한다. 실패하면 색 취향을 되돌리지 말고 토큰 누락·값 형식·연결 우회·폰트 범위 문제를 고친다. 사용자가 요청한 큰 조형·문법 변경은 이유와 화면 근거를 함께 기록한다. 단순 색 교체에 별도 승인을 요구하지 않는다.

자동 검사는 의미·아름다움·카메라의 자연스러움을 보증하지 않는다. 문서만 바꾸고 기존 장면을 새로 미감 검수했다고 보고하지 않는다. 런타임을 바꿨으면 실제 화면을 확인한다.

배포 권한과 검증 절차는 `AGENTS.md`를 따른다. 변경은 새 커밋으로 남긴다. 요청 없이 공개 이력을 다시 초기화하거나 기존 첫 커밋을 덮어쓰지 않는다.

## 9. 다음 에이전트에게 남기는 최소 메모

```text
장면과 기대 주장:
관련 심볼 원본:
쓰는 문법: 빛 / 잉크와 원본색 / 종이
보존한 사실과 설명용 단순화:
이번에 바꾼 축:
정지 대표 상태와 움직임의 의미:
미리보기 주소·해당 장면:
실시한 검사와 실제 관찰:
미확인과 남은 결함:
사용자 판정과 정확한 범위:
다음 수정에서 건드리지 않을 것:
```

현재 개인 인터뷰나 비공개 원본을 이 메모와 함께 공개하지 않는다. 프로젝트별 비공개 제작 기록은 `private/`에, 공개 가능한 아트 기준 변경은 `docs/ART_DECISIONS.md`에 남긴다.
